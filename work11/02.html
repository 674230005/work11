คำชี้แจง: ให้นักศึกษาศึกษา Class Diagram ด้านล่าง แล้วทำกิจกรรมทุกส่วนให้ครบถ้วน

จุดประสงค์การเรียนรู้:

  • อธิบายแนวคิด Encapsulation และ Tell Don't Ask จากแผนภาพได้
  • ออกแบบ Domain Exception แยกจากความผิดพลาดเชิงเทคนิคได้
  • เขียนโค้ดควบคุม invariant ของยอดคงเหลือได้
  • ทดสอบกรณีผิดพลาดและอธิบายผลลัพธ์ได้

ส่วนที่ 1: อ่านแผนภาพแล้วตอบคำถาม (10 คะแนน)

1) Stereotype «Invariant» ที่กำกับคลาส BankAccount สื่อความหมายว่าอย่างไร 2 คะแนน

คำตอบ: Invariant คือกฎที่ต้องเป็นจริงตลอดอายุบัญชี เช่น ยอดคงเหลือห้ามติดลบ และการฝาก/ถอนต้องเป็นจำนวนบวกมากกว่าศูนย์

2) สัญลักษณ์ + และ - หน้าสมาชิกของคลาส หมายถึงอะไร 2 คะแนน

คำตอบ: + คือ public และ - คือ private

3) property balance อ่านได้จากภายนอกแต่แก้ไขโดยตรงไม่ได้ ใน PHP 8.4 ใช้กลไกใด และเหตุใดจึงออกแบบเช่นนั้น 2 คะแนน

คำตอบ: ใช้ public private(set) float $balance ให้อ่านได้แต่แก้จากภายนอกไม่ได้ เพื่อให้ยอดเปลี่ยนผ่าน deposit(), withdraw() และ transferTo() เท่านั้น

4) จงระบุ Invariant ของคลาส BankAccount มา 2 ข้อ 2 คะแนน

คำตอบ: ยอด balance ต้องไม่ติดลบ และจำนวนเงินฝาก/ถอน/โอนต้องมากกว่า 0

5) ลูกศร “Domain Rule” และ “Validation” ชี้ไปยัง Exception คนละคลาส หมายถึงความแตกต่างอย่างไร 1 คะแนน

คำตอบ: InvalidArgumentException ใช้กับข้อมูลนำเข้าไม่ถูกต้อง เช่น จำนวนเงินไม่เป็นบวก ส่วน InsufficientFunds ใช้กับกฎธุรกิจเมื่อยอดเงินไม่พอถอนหรือโอน

6) เพราะเหตุใด InsufficientFunds จึงสืบทอด RuntimeException และการมี Domain Exception ดีกว่าใช้ Exception ทั่วไปอย่างไร 1 คะแนน

คำตอบ: เป็น RuntimeException เพราะเป็นข้อผิดพลาดระหว่างดำเนินงาน และชนิดเฉพาะทำให้ผู้เรียกจับและจัดการกรณีเงินไม่พอได้ชัดเจน

ส่วนที่ 2: วิเคราะห์โค้ด (10 คะแนน)

พิจารณาโค้ดต่อไปนี้ แล้วตอบคำถาม

<?php declare(strict_types=1);

final class InsufficientFunds extends RuntimeException {}

final class BankAccount
{
    public private(set) float $balance = 0.0;

    public function __construct(public readonly string $accountNumber) {}

    public function deposit(float $amount): void
    {
        $this->assertPositive($amount);
        $this->balance += $amount;
    }

    public function withdraw(float $amount): void
    {
        $this->assertPositive($amount);

        if ($amount > $this->balance) {
            throw new InsufficientFunds('Insufficient balance.');
        }

        $this->balance -= $amount;
    }

    public function transferTo(self $target, float $amount): void
    {
        $this->withdraw($amount);
        $target->deposit($amount);
    }

    private function assertPositive(float $amount): void
    {
        if ($amount <= 0.0) {
            throw new InvalidArgumentException('Amount must be positive.');
        }
    }
}

1) โค้ดส่วนใดป้องกันการฝากหรือถอนจำนวนติดลบและศูนย์ 2 คะแนน

คำตอบ: เมธอด assertPositive($amount) ตรวจว่าจำนวนเงินต้องมากกว่า 0 ก่อนฝากหรือถอน หากไม่ใช่จะโยน InvalidArgumentException

2) เมื่อเรียก deposit(300) แล้วเรียก withdraw(120) ค่า balance จะเป็นเท่าใด จงแสดงวิธีทำ 3 คะแนน

คำตอบ: เริ่ม 0 บาท ฝาก 300 ได้ 300 แล้วถอน 120 เหลือ 300−120 = 180 บาท

3) หากยอดคงเหลือ 180 แล้วเรียก withdraw(500) จะเกิดอะไรขึ้น เพราะโค้ดบรรทัดใด 3 คะแนน

คำตอบ: เกิด InsufficientFunds เพราะ 500 มากกว่า balance 180 โดยมีเงื่อนไข if ($amount > $this->balance) ก่อนหักเงิน

4) หากภายนอกคลาสเขียนว่า $a->balance = 9999; จะเกิดผลใด เพราะเหตุใด 2 คะแนน

คำตอบ: เกิด Error เพราะ balance เป็น public private(set) จึงเขียนค่าจากภายนอกคลาสไม่ได้

ส่วนที่ 4: ทดสอบและบันทึกผล (12 คะแนน)

รันโค้ดที่สมบูรณ์ตามลำดับขั้นตอน แล้วบันทึกผลแต่ละกรณี (กรณีละ 2 คะแนน)

ส่วนที่ 5: สะท้อนคิดเชิงออกแบบ OOAD (6 คะแนน)

1) คลาส BankAccount แสดงถึง Single Responsibility Principle อย่างไร 2 คะแนน

คำตอบ: BankAccount รับผิดชอบรักษายอดเงินและกฎการฝาก ถอน โอน ไม่ควรทำหน้าที่ส่งอีเมลหรือจัดการหน้าจอด้วย

2) หลัก “Tell Don't Ask” หมายความว่าอย่างไร และเมธอด transferTo สะท้อนหลักการนี้อย่างไร 2 คะแนน

คำตอบ: Tell Don’t Ask คือสั่งให้ออบเจ็กต์ทำงานแทนการดึงข้อมูลไปตัดสินใจจากภายนอก transferTo() สั่งบัญชีต้นทางถอนและบัญชีปลายทางฝากภายใต้กฎของแต่ละบัญชี

3) เหตุใดจึงควรสร้าง Domain Exception อย่าง InsufficientFunds แทนการใช้ Exception เดียวทุกกรณี 2 คะแนน

คำตอบ: Domain Exception ระบุสาเหตุทางธุรกิจอย่างชัดเจน ทำให้ระบบแยกกรณีเงินไม่พอออกจากข้อมูลจำนวนเงินผิดรูปแบบและจัดการได้เหมาะสม
